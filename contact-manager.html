Artifact and purpose

I selected the Java Contact Service and its JUnit tests from CS 320, Software Test, Automation, and Quality Assurance. The original source and test files were published in my course repository in February 2026. The artifact models contacts and supports adding, deleting, and changing individual fields in an in-memory HashMap. It does not provide a user interface or preserve records after the process ends. The November 2026 enhancement turns that foundation into a local command-line contact manager with persistent JSON storage. The accompanying ZIP preserves all four original Java files separately from the enhanced application and tests.

This artifact belongs in my ePortfolio because it connects my software development and cybersecurity interests through a practical reliability problem. A user needs valid contacts to survive a restart and needs a failed edit to leave existing information intact. Expanding a small service into a complete workflow demonstrates architectural judgment, interface-based design, and verification. Those are more substantial improvements than repairing validation or cleaning up comments alone.

Improvements and demonstrated skills

The enhanced application separates responsibilities into presentation, service, domain, and persistence layers. ContactCli handles prompts and feedback; ContactService coordinates operations; the immutable Contact record enforces field rules; and ContactRepository defines the storage boundary. InMemoryContactRepository supports isolated tests, while JsonFileContactRepository provides disk storage. Main connects these components. Users can add, find, list, edit, and delete contacts, with confirmation before deletion and deterministic ordering by contact ID.

The most important design decision is the commit boundary. An edit constructs a complete, validated replacement contact, copies the current collection, and asks the repository to save that candidate. The live collection changes only after the save succeeds. Removing mutable setters also prevents callers from changing a stored record through a shared reference. Validation retains the original length limits, rejects blank or unsafe text, and requires exactly ten ASCII phone digits. The tests verify that an invalid address cannot leave an earlier name or phone change behind.

The file repository writes a temporary snapshot in the same directory, flushes its contents, and requests atomic replacement. If atomic replacement is unsupported, it reports failure without attempting a non-atomic fallback. This follows the provider-dependent behavior of Java’s file API (Oracle, n.d.). A process lock prevents cooperating application instances from opening the same store simultaneously. Strict JSON parsing checks field names, types, duplicates, and required values, then invokes the Contact constructor. Gson’s documentation explains why strict parsing and constructor validation need deliberate handling rather than reliance on default deserialization (Google, n.d.).

The completed verification includes 55 passing enhancement tests and all 8 unchanged original tests. The enhancement suite covers user commands, validation boundaries, duplicate IDs, incomplete input, storage reopening, malformed files, and injected write, move, and unsupported-atomic-operation failures. Four separate application processes additionally verified saved data after restart, persisted edits, deletion, and refusal to open corrupted data. The ZIP includes the actual test output and process transcript. These results establish the tested behaviors; they do not claim universal filesystem reliability or complete security.

Course outcomes and coverage

The implementation provides the planned evidence for Outcome 4 by using Java, repository interfaces, Gson, and JUnit to deliver a usable persistent application. It provides evidence for Outcome 5 through immutable records, input validation, bounded file reads, rejection of malformed data, owner-only POSIX storage permissions, and errors that avoid printing contact values. Tests connect those controls to specific failure cases. Storage remains unencrypted, and the operating-system account remains the access boundary; this is a single-user local application.

Outcome 3 is supported by explicit tradeoffs. A sorted map makes listing predictable, but snapshot validation and copying cost additional work, and every successful change rewrites the JSON store. With a maximum of 1,000 contacts and a 1 MiB file limit, that simplicity is appropriate for this demonstration; a larger or concurrent application would justify a database. Outcome 2 is supported by the narrative, documented source decisions, setup directions, and requirements-to-test mapping. My earlier code review supplies the oral communication component of the broader portfolio.

Outcome 1 remains in progress. My instructor’s Module One feedback endorsed the proposed architecture, persistence, transactional updates, and validation strategy, so I retained that scope. The decision log and review questions make the work reviewable, but I am not claiming that a local log alone proves collaboration or that later feedback has already been incorporated. Reflection on learning and challenges

This enhancement clarified the difference between validating a field and protecting an operation. The original service could validate each setter independently, yet a sequence of setters could change earlier fields before a later field failed. Treating the proposed record as one immutable candidate makes the operation’s success condition explicit. It also makes tests easier to understand: a rejected operation must preserve both the prior in-memory object and the saved bytes.

Persistence introduced a second challenge: application state and file state must agree about when a change becomes successful. The small AtomicFileStore interface made failure injection possible without depending on unreliable permission tricks. A partial temporary write, a failed move, and unsupported atomic replacement can be tested separately. The tests also distinguish those controlled failures from power loss, hardware faults, and hostile same-account changes, which are outside the guarantees of this project.

Another lesson was that safe failure needs usable communication. A corrupt store is not an empty address book, and a failed save must not display a success message. Startup therefore refuses invalid data instead of resetting it, while the user guide explains how to preserve the file and restore a valid backup. Review also exposed a broken-input-stream case that could repeatedly redisplay the menu; the corrected implementation exits cleanly, and a regression test now covers it. I am more confident in explaining where each responsibility belongs and what evidence supports each claim. As milestone feedback becomes available, I will use it to refine the documentation and recovery guidance before the final portfolio submission.
