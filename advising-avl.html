Artifact and reason for inclusion

My artifact is the C++ ABCU Advising Program from CS 300. The original coursework was added to my portfolio repository on August 20, 2026; I selected that version for the CS 499 enhancement plan in October and enhanced it in November. It loads course records from a simple CSV file, lists them in alphanumeric order, and displays a course with its prerequisites. I selected it because its unbalanced binary search tree exposes a practical algorithmic weakness: already-sorted course numbers create a long chain. Replacing that structure with an AVL tree demonstrates how a data-structure decision affects predictable performance while preserving the advising workflow.

Enhancement and algorithmic reasoning

The enhancement follows my Module One plan: an AVL index, four rotation cases, invariant tests, controlled benchmarks, and explicit input limits. Each node stores its height. After insertion, the algorithm updates heights and applies a single or double rotation when the child-height difference exceeds one. The ordering relationship is preserved during each rotation. This makes worst-case lookup and insertion O(log n), compared with O(n) in the original tree; building n records becomes O(n log n) instead of O(n²) on ordered input. These bounds assume bounded key length, which the loader enforces at 32 bytes. Huang (n.d.) explains the height and rotation principles behind this behavior. The new source separates the record, tree, and existing application workflow so a reviewer can inspect the algorithm directly.

The tradeoff includes height storage, rotation work, and more implementation complexity. A hash table would provide expected constant-time lookup but would require sorting for ordered output. A sorted vector could also work well for a mostly static catalog; AVL supports incremental insertion without shifting later records. Ordered traversal remains O(n) node visits. My implementation collects an ordered vector, adding temporary record copies and storage. With n courses, p prerequisite references, and B input bytes, bounded-record loading takes O(B + (n + p) log n), including reference checks. Documentation explains the extra copying and per-record prerequisite duplicate checks so the tree bounds are not mistaken for the cost of the entire program.

Verification and measured tradeoffs

The completed enhancement passes 37 C++ test groups under AddressSanitizer and UndefinedBehaviorSanitizer, with no reported errors in those runs. The tests independently recompute height and balance and compare ordered results against std::map after every insertion in sorted, reverse, and shuffled sequences of 2,000 records. They also cover duplicates, missing courses, malformed data, I/O failure, and exact input boundaries. Seven real command-line scenarios produce output identical to the original application. This matters because a faster index would be a regression if it changed valid course results or discarded a catalog after a rejected load.

I benchmarked 100, 1,000, and 5,000 records using identical data and compiler settings for both trees. Each case used one warmup and five measured trials, alternating execution order. The lookup batch contained n successful searches and n misses above the maximum key, shuffled with seed 499. Timing excluded file I/O, output, traversal, and destruction; both implementations included comparison counters. The table summarizes the 5,000-record medians. All trials and conditions are included in the ZIP. The miss distribution favors the reverse-ordered baseline, and these synthetic measurements do not predict every real advising workload.

For sorted input, insertion comparisons fell from 24,995,000 to 113,618. The median lookup batch decreased from 283.819 ms to 1.130 ms. However, AVL construction was about 9.7% slower for 5,000 shuffled records, and the original tree was faster in both measurements for 100 shuffled records. I learned to separate worst-case guarantees from constant-factor costs. The benchmark supports the choice for predictable performance; the invariant argument explains the asymptotic guarantee.

Course outcomes and reflection

The strongest alignment is Outcome 3: I implemented and evaluated an algorithmic solution while explaining alternatives and costs. Outcome 4 is supported by the runnable C++ program, compiler checks, test harness, and reproducible measurements. Outcome 5 is supported by bounded input and failure tests. The loader accepts at most 2 MiB, 10,000 courses, 4,096 bytes per line, and 32 prerequisites per record. It rejects invalid input before replacing the active catalog. The original already used candidate-state replacement; I preserved that strength and added resource controls. The program remains a local advising tool without authentication, and indirect prerequisite-cycle detection remains outside scope.

The main implementation challenge was keeping rotation links and cached heights consistent. Updating the demoted node before its new parent, then checking invariants after every insertion, made that reasoning testable. A second challenge was measuring tree behavior without including unrelated work. Deriving an instrumented baseline from the unchanged original and checking equivalent results outside timed regions made the comparison more credible. This process strengthened my ability to justify an optimization with evidence and to report results that complicate my initial expectation.

The planned implementation and measurement work is complete. The narrative, README, and comments support the written portion of Outcome 2, consistent with the module guidance to explain intent, efficiency, and time complexity (Southern New Hampshire University [SNHU], n.d.). Outcome 1 still needs evidence of feedback affecting decisions; documenting review questions alone does not complete it. The database enhancement is now implemented and tested. My remaining portfolio work is to incorporate milestone feedback as it becomes available, publish the database artifact, and connect the artifacts in the professional self-assessment. I would especially value feedback on whether the benchmark workload and chosen input limits adequately support the advising use case.
